# KKxtti 3.3.0: deep engineering review and improvement plan

**Review date:** 22 October 2026. **Baseline:** the 3.3.0 package in this workspace; published repository commit 25d8f91b994c99fa4e5ac1b1ea2a008431162e04. **Separate change:** the requested 3.4.0 NVIDIA potato-profile correction. See RELEASE-STATUS.md for what was actually changed and published.

This is a source review and a proposed engineering plan. Reproduction procedures below are designs for disposable VMs or mocks, not claims that they were executed. No gameplay, photon-latency, thermal, anti-cheat, physical NIC, power-loss or clean-VM measurements were performed for this review. A successfully written registry value is not proof that a feature consumed it.

## 1. Executive summary: ten highest-impact changes

The strongest part of the project is its existing intent: individual selections, saved before-values, many conflict checks, constrained native tools, explicit irreversible-action warnings and refusal to promise measured gains. The biggest opportunity is to make those guarantees consistent across every route and measurable across releases.

Effort: S = about 0.5–2 developer days; M = 3–7 days; L = 2–6 weeks, before broad hardware validation. These are planning estimates for one maintainer, not delivery commitments. Impact and implementation risk are my engineering judgments; confidence is high unless stated otherwise.

| Rank | Change | Rationale and impact | Implementation risk | Effort |
|---|---|---|---|---|
| 1 | Enforce preview/write capability at one backend boundary | Direct control Undo and NIC handlers bypass the main preview gate. Prevents unexpected writes during demonstrations and testing. | Low for immediate guards; medium for dispatcher migration | S then M |
| 2 | Replace legacy boot Undo with expected-state recovery | Current BCD restore can overwrite later edits. Boot configuration deserves stronger checks than ordinary preferences. | High if legacy records are automatically migrated; fail closed instead | M |
| 3 | Keep the UI under the initiating user; elevate only machine operations | Alternate administrator credentials currently redirect HKCU, Appx and game paths to another account. | Medium; IPC and identity checks need deliberate design | L |
| 4 | Ship signed, immutable releases with a protected execution location | Hashes embedded in a mutable remote launcher cannot authenticate that launcher; user-writable code is loaded again after launch. | Medium; signing eligibility and packaging work | M–L |
| 5 | Introduce state v2 with stable storage, resource snapshots and serialized recovery | Per-release history, fixed temporary names and catalog-index references undermine durable Undo. | Medium; migration must preserve originals | L |
| 6 | Put applicability and effective-state evidence into catalog v2 | A generic minimum build and a successful write overstate support for private preferences, browser policies and staged features. | Low for honest labels; medium for detectors | M–L |
| 7 | Build a repeated A/B/A experiment workflow | This creates useful evidence for the actual machine and game, including uncertainty and regressions. | Medium; capture semantics and experimental design matter | L |
| 8 | Make app removal a dependency-aware, reversible-where-possible inventory | Current-user scope is good; reinstalling software does not restore lost application data. | Medium; maintained per-package recipes | M |
| 9 | Separate GPU driver profiles, game files and hardware guidance | The potato-page flaw is a real product error. Runtime capability detection must replace historical reference-PC assumptions. | Medium; driver acceptance does not prove rendering effect | M |
| 10 | Make release evidence reproducible, accessible and consistent | UI route coverage, parser fuzzing, clean-VM checks, keyboard/UIA work and one generated verification report reduce regressions. | Low to medium | L |

### Scope and method

The review read the production PowerShell engines, all production C# sources, launcher/build files, catalog, research data, guides, audit page, manifest and supplied test sources. The 104 controls reconcile as 16 built-in entries plus 88 catalog entries. Existing tests were inspected, not treated as proof of current runtime behavior. Historical notes remain distinguishable from current code.

Evidence labels used throughout:

- **D — documented:** a primary source describes the mechanism. It does not establish a gaming benefit.
- **M — measured:** a reproducible measurement with identified workload/hardware. No new M evidence was produced here.
- **F — folklore/reference:** an implementation or community recipe without sufficient vendor support or controlled evidence.
- **I — inference/proposal:** reasoning from source or an engineering design. It must be tested.
- **Confidence:** high for direct source observations; medium for mechanisms with uncertain applicability; low for unverified performance effects.

**Current Windows applicability:** Microsoft's release table lists 26H2 (GA 2026-09-29), 26H1 (GA 2026-02-10, targeted new hardware), 25H2 and 24H2. The 2026-10-13 table lists 26300.9711, 28000.3231, 26200.9711 and 26100.9711 respectively. A numerical build comparison is insufficient: the 26H1 hardware branch is not a universal successor to the 26H2 servicing branch. Home/Pro and Enterprise/Education also have different servicing lifetimes. Treat these as documented targets for a validation matrix, not tested support. [Windows release information](https://learn.microsoft.com/en-us/windows/release-health/windows11-release-information).

### Cross-cutting conclusions and positive controls

**Registry semantics.** Off=null means remove the utility's explicit value, not “set Windows default,” not “disable the feature,” and not exact Undo. Exact Undo restores the recorded prior existence, type and data. Preserve empty REG_SZ separately from absent values; default-value names may be empty strings. ExpandString must be read without environment expansion; MultiString needs ordered arrays; Binary needs canonical bytes. HKU/.DEFAULT is not a template for every newly created user: do not market numlock-logon as “all users.” Explicitly identify SYSTEM/logon context, and keep the mapping unverified until its effective behavior is demonstrated. [Registry views](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/view-system-registry-with-64-bit-windows).

**Concurrency.** Expected-state checks reduce accidental clobbering but are not an atomic registry compare-and-swap. A utility lock serializes this utility only; GPO, Windows, other tools and games can still write concurrently. Re-read immediately before each write and after the transaction, retain conflicts, and never claim a distributed transaction across registry, BCD, files, drivers and Appx.

**Process invocation.** The fixed native executable allowlist, absolute system-tool paths, UseShellExecute=false and rejection of embedded quotes/newlines are useful. The WPF bridge passes user values as runspace variables rather than interpolating adapter names into PowerShell code; no concrete user-string command-injection exploit was established. Preserve this. The prefix-based preview classification should become a fixed operation table. Resolve system paths from trusted Windows APIs and make x64 an explicit engine requirement. PowerShell execution policy is not an authentication boundary. [Execution policies](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies).

**Dangerous actions.** Current OS-encryption blocking for automatic BCD edits is worth retaining; do not suspend encryption to force timer tweaks through. Hibernation changes must record enabled/type/size and show Fast Startup/sleep implications, without claiming a speed benefit. Appx deletion, Recall deletion and encryption changes have different recovery capabilities; one green “Undo available” badge must not cover all three. NIC/DNS edits need an explicit selected interface identity, capability list and reconnect notice; a VPN/driver change invalidates stale plans. Game editing must stop when processes are open, preserve bytes/encoding, and retain a conflict if a launcher or cloud sync rewrites the file.

**Reparse/ZIP hardening.** The launcher's stricter entry validation and complete manifest coverage are useful safeguards against malformed archives. They do not authenticate a modified launcher or resolve later mutable-code loads. A protected destination and single extractor are preferable to repeating slightly different string checks.

### Measurement assessment

FrameAnalysis.cs is not wrong merely because it uses nearest-rank p99 or the mean of the slowest 1%: both are defensible when named precisely. The existing mean-FPS calculation, reciprocal of mean interval, should be retained. The weakness is experimental interpretation and import semantics, not an established arithmetic defect.

PresentMon **2.6.0**, published 2026-09-21, is the current release found during this review. Its release adds display attribution and availability reporting. The 2.5.0 binary distribution was withdrawn, and 2.5.1 corrected several metric/API issues. Pin a version and schema; do not infer semantics from the word “PresentMon” or from a current README alone. [Release history](https://github.com/GameTechDev/PresentMon/releases).

The complete import contract, formulas, A/B/A protocol, confidence intervals, quality gates and acceptance cases are in [STATISTICS-SPEC.md](STATISTICS-SPEC.md).

### Adopt, avoid and qualify

- **WinUtil:** adopt discoverability, curated grouping and reusable catalog structure. Its broader scope and presets are not evidence that every tweak is beneficial. Do not use its implementation as a substitute for Windows applicability documentation.
- **Sophia:** adopt version-specific packaging, localization and individually callable functions. Its 8.0.0 release is dated 2026-10-11; current Windows 11 requirements are 25H2+. Restore-default functions should not replace recorded prior-value recovery.
- **O&O:** adopt current session history, clear blocked-setting feedback, search and keyboard work. Current documentation includes richer Undo and premium drift enforcement, so an older comparison would be misleading. Prefer notifying about drift over repeatedly fighting organizational or security policy.
- **privacy.sexy:** adopt visible generated changes, structured script metadata and transparent build infrastructure. Revert scripts need scrutiny for exact prior-state preservation. Do not copy AGPL code into a differently licensed project without resolving obligations.
- **Winhance:** adopt searchable software/feature categories and configuration portability. Its current license is PolyForm Shield, with restrictions on competing redistribution; source visibility is not blanket permission to reuse its code. Evaluate UI ideas independently.
- **Atlas/Revi:** adopt prerequisite documentation and explicit recovery limits. Do not reproduce broad security trade-offs. Current Atlas warns that uninstall requires Windows reinstall; Revi now documents a 25.10+ repair path preserving files/apps, so claiming both always require a clean reinstall would be inaccurate.
- **PowerToys:** adopt settings search, theme/localization, diagnostics export and permissions clarity. It solves different problems and is not evidence for a debloat/FPS claim.

The proposed competitive advantage is evidence tied to a reversible change on the user's own machine. None of the reviewed comparison pages established the complete repeated experiment contract proposed here.

### Skeptical review corrections

The final review deliberately retained these qualifications:

- Preview flaws are concrete source paths; mutable elevated code requires a local writer/approved elevation and was not called a silent UAC bypass.
- Existing registry and game readback/conflict protections are acknowledged. They reduce risk without creating an OS-wide atomic transaction.
- FrameAnalysis's nearest-rank p99 and worst-tail mean are not conflated or accused of being arithmetically wrong.
- Primary settings-portability documentation is not automatically a supported write API. Similar-looking values/types were not treated as exact matches.
- Current Edge account/version constraints, Brave version gates, legacy Copilot deprecation and Notepad app version matter.
- Current Start HideRecommendedSection policy documentation includes Pro; older Enterprise-only assumptions were corrected.
- Current inbox-app removal policy documentation includes 24H2+, not only 25H2.
- O&O now documents richer Undo; Winhance's current license is not ordinary permissive OSS; Revi's current repair-reinstall path differs from Atlas.
- Current MPO guidance includes benefits, contradicting routine disabling. Current Fortnite renderer guidance weakens claims that a saved NVIDIA LOD override must visibly work.
- Signing eligibility and new-file SmartScreen behavior were checked rather than assuming EV eliminates warnings.
- Pester 5 is the requested maintenance line, not the latest major. PresentMon producer and metric semantics must be pinned.
