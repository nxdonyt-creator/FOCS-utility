Corrections included in 3.3.0

  1. Recall: corrected the false claim that existing snapshots were preserved. Added permanent-deletion confirmation when applying or restoring the deletion policy, including through Reset all.
  2. Recovery conflicts: a system-state change during confirmation no longer triggers an unconditional rollback write. Registry, NIC and DNS rollback preserves unrelated newer values and leaves a recovery record.
  3. Power switching: confirmation and Undo now check the active plan instead of overwriting a newer choice.
  4. Policy accuracy: corrected Explorer search scope, Recall edition/revision eligibility and Notepad requirements. Marked legacy Copilot policy deprecated and removed machine-specific claims from shared control notes.
  5. Video integration: read-only inspection of 12 values, an optional MMCSS 10%/20% comparison with exact registry-state Undo, and explanations for rejecting unsupported blanket tweaks. The UI blocks control writes in preview mode.
  6. Presentation: renamed the desktop-effects preset to describe its actual function and clarified that Undo cannot reconstruct deleted data.

Evidence and limits

Every control's declared values, scope, description and recovery route were inspected. Higher-impact and disputed claims were checked against primary Microsoft/vendor documentation. Some shell preferences still rely on reference implementations; they are identified by their evidence labels and should be checked in the actual Windows/app UI.

This is a source and documentation audit, not a demonstration of an FPS increase. Earlier 3.3 development checks covered mocked registry/launcher behavior and native construction. The final audit changes were compiled and parsed, but those earlier test totals must not be represented as validation of every final behavior. No game benchmark, hardware latency measurement, full interactive native walkthrough, fresh antivirus scan or code signing is claimed.

Sources describe supported mechanisms. They do not prove a benefit on this PC. Hardware rollout, browser profile, Windows edition, installed app version and organization policy can make a stored registry value ineffective.

3.4.0 correction: NVIDIA Potato graphics

The Games page now applies a Fortnite NVIDIA driver profile with texture LOD bias +1.5 or +3.0, high-performance texture filtering and a 1x anisotropic override. The previous INI editor is separately labeled and collapsed.

Inspect shows the selected profile and current values. Reset selects the latest NVIDIA potato record and restores prior overrides or inheritance. The competitive NVIDIA profile has its own Reset selection.

Epic reports that the DirectX 11 option has been removed. Current Fortnite uses DX12, so the visual effect of these driver overrides must be checked on the actual driver/game combination. Saved values do not prove reduced texture detail or an FPS gain.

Upstream setting definitions

Gaming power plan

Six supported AC options on a separate copy of the current desktop plan: minimum CPU 5%, maximum 100%, boost mode 2, EPP 0, autonomous mode 1 and PCIe link-state power saving 0. Unsupported optional settings are skipped. More aggressive performance preferences can increase heat/power without improving a CPU- or GPU-bound game. Keep the original plan for comparison. Undo checks the created plan fingerprint.

Balanced / High performance / Ultimate

Compare with your real workload; the plan name is not proof of speed. The simple plan switch now rechecks changes during confirmation and refuses to overwrite a newer active plan during Undo. Frame caps, V-Sync and rendering preferences are game-specific. The engine preserves encoding and unrelated fields and checks the expected file bytes before atomic replacement. Primary or implementation reference

RSS, checksum offload and LSO

Keep driver-supported offloads as a starting point. They reduce or distribute CPU packet work; disabling everything is not a universal latency fix. Only the selected physical adapter and driver-advertised values are changed. Throughput, packet loss and CPU load should accompany any comparison.

Primary or implementation reference

Interrupt moderation and EEE

Experiments only: disabling moderation can trade packet batching delay for more CPU interrupts. Disabling Energy Efficient Ethernet can increase idle power. Results depend on NIC, driver and traffic. Explicit reconnect is separate; a saved setting may not be active until then.

Primary or implementation reference

DNS profiles

A resolver change affects name lookup, filtering and potentially service selection; it does not guarantee a lower RTT to an already connected game. Local/organization names can break. Both IPv4/IPv6 automatic versus static modes are backed up, and rollback now preserves unrelated newer values.

Primary or implementation reference

Network probes

Thirty default ICMP samples to the gateway and public anycast services indicate reachability/RTT on the selected route. They do not measure game-server latency, packet scheduling under load or bufferbloat. Compare actual game telemetry under normal traffic before changing more settings.

Primary or implementation reference

Hibernation and reserved storage

Disk-space controls. Hibernation off also removes Fast Startup; reserved storage helps servicing when space is constrained. Neither is an established FPS tweak. Preserve adequate disk space and normally keep reserved storage enabled. Pending servicing can require manual recovery after restart.

Primary or implementation reference

Recall optional feature

DISM controls only a feature that exists on this installation, without automatic restart or component-payload removal. Feature re-enable is not a snapshot-data backup. The separate snapshot policy has an explicit permanent-deletion confirmation.

Primary or implementation reference

Maps / media-sharing / Fax services

Changes startup mode to Manual; does not stop a running service. Retain services for features you use. These three optional services are not evidence that all Windows services should be disabled. System-change rollback now stops before overwriting an external value.

Primary or implementation reference

Boot override reset

Removes only four allowlisted timer/CPU-count overrides and exports BCD. Restricted to a decrypted OS volume; no suspension of encryption or Secure Boot. Legacy boot restore is an explicit restoration of saved values, which can reintroduce a bad prior tweak; it is not part of newer Reset all. Use only to undo a known override and keep recovery media.

Primary or implementation reference

Debloat and desktop uninstall

Removal can save space and eliminate active work only if the removed app was running. App data can be lost. Package manifests are not data backups or guaranteed reinstall. Store, frameworks, drivers, gaming services and unknown/system packages stay protected. Do not remove apps simply to maximize a removal count.

Primary or implementation reference

Temporary-file cleanup

Only old files in the user temp directory; locked files/links are skipped. No shader-cache purging, Downloads cleanup or unattended Windows Update cleanup. Deletion has no Undo. Disk-space housekeeping is not evidence of improved FPS.

Primary or implementation reference

BitLocker decryption

High-impact storage-security action with a DECRYPT confirmation and no automatic encryption Undo. Retain encryption unless you deliberately need decryption. The audit found no basis to recommend it for gaming.

Primary or implementation reference

Installer and external tools

Allowlisted WinGet packages use the official source. Installs/uninstalls have their own data and update implications. Chromium snapshots are development builds without automatic updates; they are not a generally preferable browser. Profile Inspector is a pinned third-party binary, not a guaranteed-safe or automatic profile import.

Primary or implementation reference

Peripheral tools

Connected-device detection and input event timing are observational. Windows event arrival intervals are not electrical USB polling measurements or end-to-end latency. Use manufacturer tools for polling/firmware; compare high-rate input while watching frame times and CPU load.

Primary or implementation reference

Frame-time comparison

Reports average FPS, slowest-1% average-derived FPS, p95/p99, worst frame and missed frame budget from comparable capture metrics. Invalid rows are counted. Repeat warmed A/B/A runs; one pair does not establish a winner. Frame time is not click-to-photon latency, and FPS samples are not independent trials.

Primary or implementation reference

Backups, recovery and Reset all

Registry type/value/absence, driver properties, DNS mode, game fields and supported profile state are saved locally. Conflicts stop recovery. Registry/network/DNS rollback now checks for unrelated current values before writing. Reset all retains destructive Recall confirmation. No mechanism can guarantee atomicity against a simultaneous external writer; close other editors. App data, deleted files, encryption and older release journals are excluded.

Primary or implementation reference

A comparison you can trust

  1. Record Windows/game/driver versions, display mode, resolution, FPS cap, power plan and background programs. Save the current settings.
  2. Warm up the game and shader cache, then capture the same representative scene for at least 60 seconds. Avoid comparing a menu with gameplay.
  3. Change one meaningful setting. Restart when its documentation requires it. Repeat baseline/changed/baseline sessions and compare at least three captures per state.
  4. Check average FPS, 1% low and p99 frame time alongside temperatures, visual clarity, audio, stability and normal background activity. Compare differences with the variation between runs.
  5. Keep a change only if the benefit repeats and its tradeoffs are acceptable. Use real input-to-photon measurement for input latency and the game's own telemetry for its network RTT.

Do not treat a single best run, a lower process count or an idle RAM screenshot as proof of better gameplay.
